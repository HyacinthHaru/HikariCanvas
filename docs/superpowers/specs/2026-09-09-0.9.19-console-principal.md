**日期**：2026-09-09
**版本**：0.9.19（计划）
**状态**：设计待过目
**作者**：HaruHyacinth

---

## 0. 目标

让服主**不进游戏**、直接在服务端控制台管理画布：

```
> canvas open w-aaaabbbb
[HikariCanvas] wall w-aaaabbbb (alias: 车站牌) 3x4 张地图
[HikariCanvas] 编辑器链接（15 分钟内有效，仅可用一次）：
[HikariCanvas] http://127.0.0.1:8765/?token=<43 字符>

> canvas delete w-ccccdddd
> canvas delete w-ccccdddd confirm
```

控制台能打开 / 删除 / 改别名 / 列出**任何**画布，包括别人锁定的。

**这不是"给命令松一个 `instanceof` 判断"**。真正要解决的是：整条鉴权链的输入是 `UUID`，
而"控制台"不是一个 UUID 能表达的主体。硬塞一个假 UUID 进去，会让全链继续以为自己在跟
玩家打交道，然后在十几处打特判——每新增一个权限节点都要记得再补一次。

## 1. 现状（2026-09-09 实测）

### 1.1 已经就绪的部分（不用改）

| 检查项 | 现状 |
|---|---|
| `SessionManager.open(UUID, String, String)` | 收 UUID + 名字，**不收 `Player` 对象** |
| `SessionManager.deleteWall(String wallId)` | **完全不带玩家** |
| `Messages.send / localeId(CommandSender)` | 已支持非玩家，回落 `defaultLocale` |
| `benchmark` / `diagnose` / `variable` 三个子命令 | **已经是控制台可用的**（`.requires(src -> src.getSender().hasPermission(...))`），现成模板 |

| 会话自动回收 | ISSUED 15min（token TTL）/ ws-grace 5min / idle 30min —— 控制台开了没人用的墙**会自己解锁** |

### 1.2 阻塞点

**（a）命令层一行门槛**

```java
// CanvasCommand.java:212
private static boolean isPlayerWith(CommandSourceStack src, String permission) {
    return src.getSender() instanceof Player p && p.hasPermission(permission);
}
```

`edit / wand / confirm / cancel / open / list / alias / delete` 八条全部挂在它上面。

**（b）权限语义反向**

会话存 UUID 不存 sender。编辑器内全链靠 `Bukkit.getPlayer(uuid)`：

```
合成 UUID → getPlayer 恒 null → online = false
  ├─ default=true  节点（var.write.own / schedule.own / rail.*）→ grantedWithDefaultTrueFallback 放行
  └─ default=false 节点（admin.* / delete.any / script.broadcast
     / var.bind / template.use-others / canvas.upload）        → 一律拒
```

实测受影响的解析点共 **15 处**：`MainThreadPerms` 的 14 个调用点 +
`UploadHandler.resolveUploadPermsDirect`（在 `image` 包，用不了 `MainThreadPerms`，
自建了一份；`p == null` 直接返 `DENY_ALL` → **控制台会话传不了图**）。

**（c）owner-only 判定恒 false**

```java
// WallOpDispatcher:129 / 155 / 186
if (!wall.ownerUuid().equals(s.playerUuid())) → FORBIDDEN   // lock / unlock / alias
```

```java
// SessionManager.open:572 —— 与本需求正面冲突
if (w.publishedAt() != null && !playerUuid.equals(w.ownerUuid())) {
    boolean bypass = live != null && live.hasPermission("canvas.admin.bypass-lock");
    if (!bypass) return Forbidden;          // live 恒 null → 控制台恒 Forbidden
}
```

前端 `project.ts:65` 的 `isOwner = (ownerUuid === selfUuid)` 也恒 false → **解锁按钮根本不渲染**。

**（d）一主体一会话**

`byPlayer` 是 `Map<UUID, String>`，`forget()` 的 `byPlayer.remove(s.playerUuid(), s.id())`
依赖这个唯一性。控制台若要同时开多面墙，得动这条不变式（见 §2 决策 3）。

## 2. 固化决策

> 这六条是本方案的骨架，实施时不得越界；要改先回来改本文档。

1. **`Session` 增加显式主体类型 `Principal { PLAYER, CONSOLE }`，UUID 从"权限依据"降级为"索引键"。**
   鉴权链一律问 `principal`，不再从 UUID 反推身份。这是整个方案的立足点——
   #1.2(b)(c) 两类问题共用一个根因，也就该有一个根修。

2. **控制台会话的 UUID = nil UUID（`new UUID(0,0)`）。**
   不做成 nullable：`session.playerUuid()` 全仓 **55 个消费点、12 个文件**，改成可空是把
   一个编译期安全的字段换成运行时 NPE 面。nil UUID 天然不会与任何真实玩家碰撞，
   且 `Bukkit.getPlayer(nil)` 安全返 null。
   **它只是索引键，任何鉴权判断都不许读它。**

3. **控制台同样遵守"一主体一会话"，不做多开。**
   理由：`byPlayer` 的唯一性被 `writeLock` 临界区、`forget()`、`collectExpired` 共同依赖，
   为控制台破例要重新审计整套并发不变式——代价远超收益（需求本身是"开一面墙拿个链接"）。
   代价是"控制台开了 A 再开 B 会撞 `AlreadyHasSession`"，用 §5 的 `/canvas cancel`
   作逃生口，且 15 分钟后自动过期。
   > 若你认为多开是刚需，这条可以推翻，但那是独立一版的工作量，不该混进 0.9.19。

4. **token 原文允许进入控制台日志。**（作者 2026-09-09 决定）
   原禁令"token 原文禁止出现在任何 log"属过度防御：链接**单次使用 + 15 分钟 TTL +
   首次 auth 绑死 IP + per-IP 限流 10 次/分**，四道防线叠加后剩余风险可接受。
   `docs/security.md` §2.2 与威胁表 T2 同步修订（见 §7）。

5. **控制台的授权是全开，不是"当成 OP 玩家"。**
   `principal == CONSOLE` 时权限解析直接返回全授予，**不查任何权限节点**——
   与 Bukkit 对 `ConsoleCommandSender` 的既有语义一致（控制台本就拥有全部权限）。

6. **命令 sender 白名单 = Player + ConsoleCommandSender，显式排除命令方块。**
   不能简单换成 `src.getSender().hasPermission(...)`：那会让命令方块也能跑 `canvas open`，
   把 token 打进方块输出/世界数据——那是比控制台日志低得多的门槛，且服主无从察觉。

## 3. 核心设计

### 3.1 `Principal`

```java
// session/Principal.java（新）
public enum Principal { PLAYER, CONSOLE }
```

```java
// session/Session.java
public static final UUID CONSOLE_UUID = new UUID(0L, 0L);

private final Principal principal;

/** 既有构造器保持不变，默认 PLAYER —— 现存调用点零改动。 */
Session(String id, UUID playerUuid, String playerName, long now) {
    this(id, playerUuid, playerName, now, Principal.PLAYER);
}
Session(String id, UUID playerUuid, String playerName, long now, Principal principal) { ... }

public Principal principal() { return principal; }
public boolean isConsole() { return principal == Principal.CONSOLE; }
```

### 3.2 `SessionManager.open` 重载

```java
// 既有签名保留，转调新版
public OpenResult open(UUID playerUuid, String playerName, String wallIdOrAlias) {
    return open(Principal.PLAYER, playerUuid, playerName, wallIdOrAlias);
}

public OpenResult open(Principal principal, UUID playerUuid, String playerName,
                       String wallIdOrAlias) { ... }
```

`open` 内部两处改动：

```java
// 锁定墙的准入（原 SessionManager:572）
boolean isOwner  = playerUuid.equals(w.ownerUuid());
boolean canForce = principal == Principal.CONSOLE
                || (Bukkit.getPlayer(playerUuid) instanceof Player live
                    && live.hasPermission("canvas.admin.bypass-lock"));
if (w.publishedAt() != null && !isOwner && !canForce) { ... Forbidden ... }
```

控制台传 `CONSOLE_UUID` + `playerName = "CONSOLE"`。

### 3.3 权限解析：`MainThreadPerms` 改吃 `Session`

现签名 `resolve(Plugin, UUID, String[])`，改为：

```java
static Resolved resolve(Plugin plugin, Session session, String... nodes) {
    if (session.isConsole()) return Resolved.allGranted(nodes.length);   // ← 短路
    return resolve(plugin, session.playerUuid(), nodes);                 // 原路径
}
static boolean hasPermission(Plugin plugin, Session session, String node) { ... }
```

**为什么改成吃 `Session` 而不是加一个 `Principal` 形参**：14 个调用点全都已经持有
`Session`，传它不可能传错；而多加一个 `Principal` 形参，任何一处手滑写成 `PLAYER`
都会静默退化成"控制台被当普通玩家"，且和现在的 bug 长得一模一样、不会有人发现。
0.9.17 已经因为同型复制粘贴分叉修过一次（`grantedWithDefaultTrueFallback`），
不再给它第二次机会。

`Resolved.allGranted(n)` 返 `online = true` + 全 `true`：
`grantedWithDefaultTrueFallback` 首行 `granted(0)` 即命中，`online` 语义为"主体在场"，
对控制台成立。

### 3.4 三处 owner-only → `canManage`

```java
// SessionManager 新增，供后端与 ready 帧共用一个判据
public static boolean canManageWall(Session s, WallRepo.Wall w) {
    return s.isConsole() || w.ownerUuid().equals(s.playerUuid());
}
```

`WallOpDispatcher` 的 `wall.lock` / `wall.unlock` / `wall.alias` 三处判定换成它。
`wall.alias` 额外保留既有的 `canvas.alias.any` 旁路（控制台走 §3.3 已全开）。

### 3.5 `UploadHandler`

`resolveUploadPermsDirect` 的 `p == null → DENY_ALL` 前加控制台短路。
该类在 `image` 包、拿不到 `MainThreadPerms`（package-private），
但它的 `resolveUploadPerms` 入口已能拿到 `Session`（IP 绑定路径），传 `isConsole()` 布尔即可，
**不要在 `image` 包里再复制一份主体判定逻辑**。

### 3.6 `WebServer.handleAuth`

```java
// 原：live == null → new boolean[]{true, false}（放行 + 无模板 bypass）
// 改：控制台 → new boolean[]{true, true}
```

## 4. 前端与协议

### 4.1 ready 帧新增 `canManageWall`

```jsonc
{
  "ownerUuid": "00112233-…",   // 保留（展示用）
  "selfUuid":  "00000000-0000-0000-0000-000000000000",
  "canManageWall": true        // ← 新增：服务端算好的授权结论
}
```

**为什么不是让前端拿 `principal` 自己再算一遍**：`isOwner = (selfUuid === ownerUuid)`
本身就是"前端重新推导授权结论"的产物，正是 §1.2(c) 那个 bug 的来源。
授权判断只该有一个权威（服务端），前端只消费结论。

### 4.2 业务协议版本 v7 → v8

`docs/protocol.md` 定的是"每次升版取干净切换（`MIN = MAX` 同步提升，不维持双轨）"。
ready 帧 payload schema 变了，按规矩升版：

- `Protocol.SUPPORTED_MIN = SUPPORTED_MAX = 8`
- `wsClient.ts CLIENT_V = 8`

好处是浏览器里缓存的旧前端会被 close `4002` 顶掉、强制刷新，
而不是静默地不认识 `canManageWall`、让控制台用户看不到解锁按钮却查不出原因。

### 4.3 前端改动

`stores/project.ts`：新增 `canManageWall` ref 从 ready 写入；
`isOwner` **改名为 `canManageWall`** 并直接透传服务端结论（不再本地比对 UUID）。
消费点 5 处：`useLockGuard.ts:53`、`TopBar.vue:30/306/307/313`、`CanvasView.vue:1378`。

> 保留 `ownerUuid` / `selfUuid` 两个字段——它们还有展示用途，且删字段是额外的破坏性变更。

## 5. 命令层

`CanvasCommand` 新增 sender 白名单：

```java
/** Player 或控制台；**显式排除命令方块**等其他 CommandSender（见决策 6）。 */
private static boolean isPlayerOrConsoleWith(CommandSourceStack src, String permission) {
    CommandSender s = src.getSender();
    if (s instanceof Player p) return p.hasPermission(permission);
    return s instanceof ConsoleCommandSender && s.hasPermission(permission);
}
```

| 子命令 | 控制台 | 说明 |
|---|:--:|---|
| `open <id\|alias>` | ✅ | 打印明文 URL（不用可点击 Component） |
| `list` | ✅ | 现有输出已是纯文本 |
| `alias <name>` | ✅ | 作用于当前控制台会话的墙 |
| `delete <id> [confirm]` | ✅ | 二次确认桶改按 §5.1 键控 |
| `cancel` | ✅ | 决策 3 的逃生口 |
| `edit` / `wand` / `confirm` | ❌ | 本质是"拿金铲在世界里点两个方块选墙面"，无玩家实体即无 `pos1/pos2`，控制台版无意义 |

### 5.1 `delete` 的二次确认桶

现为 `Map<UUID, ConcurrentMap<String, PendingDelete>>`，按玩家 UUID 分桶；
控制台复用 `CONSOLE_UUID` 这一格即可，**无需改结构**。
`PlayerQuitEvent` 清理监听对控制台天然不触发（nil UUID 永不退服），
靠既有的 `reapExpired`（30s 窗口）回收。

### 5.2 输出

控制台走 `messages.send(sender, ...)` → `localeId` 回落服务器默认语言，无需新 i18n 机制。
新增 key：`command.open.editor-url-plain`（控制台用的无超链接版本）。
zh / en 两侧都要加——仓库有 zh/en 键集合全等测试守着。

## 6. 明确不改的东西

- **`SessionRateLimiter`（40 ops / 2s）对控制台会话照常生效。** 它是资源护栏不是授权闸，
  控制台没有豁免的理由。
- **IP 绑定照常。** 控制台签的链接由"第一个打开它的浏览器"绑定 IP，此后异地重放即拒——
  这恰恰是决策 4 能成立的关键一环，不能动。
- **`byPlayer` / `byWall` / `writeLock` 三索引结构与并发不变式**（决策 3）。
- **一墙一会话的排他锁。** 控制台开着的墙，玩家 `/canvas open` 照样 `WallOccupied`。
