## 1 这是什么

HikariCanvas 把画布渲染成地图像素，这个过程要花 CPU 和内存。画一面墙要多少毫秒、占多少内存，
都能测出来。

测试在后台跑真实的渲染代码，用 21 个预设场景。不需要真实玩家、不放地图、不影响在线的人，随时
可以跑，跑出问题也不影响服务器。

**给谁用**：想知道"我这台机器能撑多少画布"的服主。

> 这个测试只测 CPU 和内存，不测网络（带宽、延迟、压缩这些都不测）。

## 2 快速开始

```
/canvas bench run        # 后台跑全部 21 个场景，结束在聊天栏给彩色摘要
```

跑完控制台 / 聊天栏会打印 `Saved to: .../benchmarks/<时间戳>/`，进该目录用浏览器打开 **`report.html`**——
里面有环境卡、各场景耗时表、两张内联 SVG 条形图，和一个 **性能预算计算器**（填你自己的每 tick 预算 / tps /
份额 / 帧率实时算每个场景的"能放的墙数"）。零外链、零 CDN，离线也能看。

### 2.1 命令族

权限节点 `canvas.bench`（默认仅 op）。

| 子命令 | 作用 |
|---|---|
| `/canvas bench list` | 列出全部 21 个场景（id / category / tile 尺寸 / 主元素类型） |
| `/canvas bench run [selector] [iters] [warmup]` | 跑测试，落 `benchmarks/<时间戳>/` 三件产物，结束发摘要 |
| `/canvas bench report [id]` | 读最近（或指定时间戳）的 `report.json` 重新打印摘要 |
| `/canvas bench clear` | 清空 `benchmarks/` 目录内容 |

几条纪律：

- **一次只能跑一个测试**。上一个还没跑完时再跑会被拒绝（两个一起跑会互相抢 CPU，结果不准）。
- 测试在后台跑，测试期间服务器照常运行，跑完才在聊天栏发结果。
- `clear` 手动清理报告，系统不会自动删。报告攒多了占硬盘，自己决定什么时候清。它只删 `benchmarks/`
  目录里的东西。

### 2.2 selector / iterations / warmup

`run` 三个可选参数：

| 参数 | 取值 | 默认（省略时） |
|---|---|---|
| `selector` | 场景 id（如 `subway-sign-2x1`）/ category 名（`element-isolation` / `effect` / `mixed`）/ `all` | `all` |
| `iters` | 测量轮数（≥1） | 20 |
| `warmup` | 预热轮数（≥0，预热的结果不计入统计） | 5 |

例：

```
/canvas bench run                       # 全 21 场景，20 measured + 5 warmup
/canvas bench run subway-sign-2x1       # 只跑地铁屏场景
/canvas bench run element-isolation     # 只跑 9 个单元素隔离场景
/canvas bench run mixed 200 20          # 混合场景，200 measured + 20 warmup（更稳的数字）
```

`selector` 支持 tab 补全（all + 3 个 category + 21 个场景 id）。selector 无匹配场景时早退提示，不空跑。

**iters / warmup 怎么选**：预热太少，头几轮会偏慢、拉高平均值；测量轮数太少，最慢情况的数字会跳。
默认 5+20 日常够用；想要更稳的数字（比如对比两次改动），用 `200 20` 起步。

## 3 报告怎么读

### 3.1 三件产物

`run` 在 `plugins/HikariCanvas/benchmarks/<生成时刻 epoch ms>/` 落三个文件：

| 文件 | 内容 | 给谁 |
|---|---|---|
| `report.json` | 完整数据（JSON 格式） | 机器可读，方便你自己写工具处理 |
| `summary.txt` | 文本摘要（环境信息 + 各场景耗时 + 单元素成本 + 内存回收） | 在终端里看 |
| `report.html` | 完全自包含的 HTML5（内联 `<style>` + `<script>` + SVG 图，零外链） | 浏览器可视化 + 交互计算器 |

时间戳目录名就是报告 id，`report [id]` 与 `report.html` 都用它定位。

### 3.2 各场景耗时

报告主体是每个场景一行，分两段成本（渲染和调色分开算）：

| 列 | 含义 |
|---|---|
| `渲染 一般/偏慢/最慢` | 渲染一次要多少毫秒（一般 / 偏慢 / 最慢情况） |
| `调色板 一般/偏慢/最慢` | 把颜色转成地图的 248 色要多少毫秒 |
| `内存 MB/轮` | 每轮平均占用多少内存（MB）；测不到时显示 `n/a` |
| `元素数` / `地图块数` | 该场景元素实例数 / 地图分块数 |

重点看"偏慢"那一列——它代表绝大多数情况下的耗时上限，也是后面预算公式要用的数字。

21 个场景分四类，覆盖全渲染路径：

| 类别 | 场景数 | 内容 |
|---|---|---|
| 单元素隔离 `element-isolation` | 9 | text / variable-text / rect / circle / star / path / image+mask / brush / icon，各铺满一面 2×2 墙 |
| 特效 `effect` | 5 | gradient / dither / blend / opacity / text-effects（描边 + 阴影 + 发光） |
| 真实混合 `mixed` | 3 | subway-sign（地铁屏）/ welcome-wall（欢迎墙）/ dense-dashboard（密集仪表盘 ~50 元素） |
| 尺寸梯度 `mixed` | 4 | 同一密集构图在 1×1 / 2×2 / 4×4 / 8×8 下渲染，让成本随像素数缩放、可拟合回归曲线 |

场景每次生成的内容都一样，所以两次报告的差异只来自机器本身的波动，可以直接对比。

### 3.3 单个元素的成本

报告单独算出"每多画一个元素多花多少"（从 9 个单元素场景推出）：

```
每个元素的成本 = (场景渲染均值 − 空白画布渲染均值) ÷ 元素数
```

做法是先测一面空白画布的渲染耗时，再用各场景减去它，剩下的就是"多画一个这种元素"的净成本。这样
你能看清哪类元素贵——比如贴满蒙版图片的墙和纯文字墙，成本可以差很多。文字有两种场景（普通文字、
含 `${var:...}` 变量），分开列出方便看变量多花多少。

> 由于测量误差，单个元素的成本偶尔会算出一个很小的负数，报告原样保留，不会改成 0。看到负数说明
> 这个数值接近测量误差，参考即可。

### 3.4 内存回收

报告会给出整次测试期间的内存回收情况（回收次数 + 累计暂停毫秒数）。

为什么单独看内存回收：渲染每一帧都要占一块内存，刷新越快占得越频繁，频繁回收内存也会拖慢服务器。
光看耗时看不出这部分压力，所以单独统计，方便你区分到底是"算得慢"还是"内存压力大"。

> 注意：内存回收数字是整次测试的总和（含预热轮），而各场景的内存列不含预热轮，所以两者对不上，
> 别拿它们直接相减。

### 3.5 环境信息

报告顶部一张环境卡，列出 Java 版本、操作系统、CPU 核数、最大内存、内存回收方式。

这些数字只代表这台机器。换一台服务器、改了内存设置，就要重新测一遍，不能直接套用。

## 4 性能预算公式与交互计算器

报告不直接告诉你"能开几面墙"，而是给一条公式，你填自己的服务器参数算出来。

公式（`BudgetFormula`）：

```
可用预算 (ms/s) = 每 tick 预算 × tps × 分给本插件的份额%
单面墙成本 (ms/s) = 渲染耗时(偏慢值) × fps
能放的墙数 ≈ 可用预算 ÷ 单面墙成本
```

`report.html` 里这是一个**交互计算器**：填四个输入框（每 tick 预算 / 目标 tps / 份额% / 目标帧率），
内联 JS 实时算出每个场景的"能放的墙数"。默认值取自 §13.3 示例：

| 输入 | 默认 | 含义 |
|---|---|---|
| 每 tick 预算 | 50 | 每 tick 留给画布的毫秒数 |
| 目标 tps | 20 | 服务器目标 tick rate |
| 份额 % | 30 | 分给本插件的处理时间份额（其余给世界和别的插件） |
| 目标帧率 | 5 | 画布刷新率（v1 静态招牌默认值） |

> 例：50 × 20 × 30% = 300 ms/s 可用预算。某场景渲染耗时(偏慢值) = 0.5 ms、fps = 5 → 单面墙成本
> 2.5 ms/s → 可开约 120 面。

### ⚠️ 这个数偏保守，实际通常能开更多

这个数偏保守，实际通常能放得更多。它只是个大概参考，别当成硬上限。

实际渲染中有一部分工作在后台跑，不占服务器分给本插件的处理时间，所以真实能开的墙数通常比算出来
的多。把计算器结果当成一个参考量级看就行。

## 5 用实测容量设 config 软上限

Benchmark 的实战用途：把**你自己机器的实测数据**变成 config 软上限。流程：

1. **跑 benchmark**：`/canvas bench run`（建议高 iters 求稳的数字，如 `run all 200 20`）。
2. **拿偏慢耗时 + 自己的预算代入公式**：打开 `report.html`，填你服务器真实的每 tick 预算 / tps / 份额 /
   帧率，看你常用画布尺寸对应场景（如地铁屏看 `subway-sign-2x1`、大欢迎墙看 `welcome-wall-4x2` /
   `size-4x4`）的"能放的墙数"。
3. **据此把 config 上限设成你舒服的安全上限**：把 canvas 尺寸上限 / 帧率上限等 `config.yml` 项，设成一个
   你认为安全的值——留足余量（这个数偏保守，但机器还要跑别的东西，别开太满）。

`config.yml` 里的上限是一道安全护栏，默认取宽松值，由你按自己机器主动收紧。

## 6 已知局限

当前版本有几处地方测得不够精确，列在这里供参考：

- **图标元素**：矢量图标目前走占位渲染，真实成本会被低估。
- **图片**：图片场景用的是一张固定的测试图，和你真实上传的图片在尺寸、解码上有差异，成本只是大致估算。
- **整体成本偏保守**：公式把整个渲染都算进服务器的处理成本，实际有一部分在后台跑，所以算出来偏保守。

设计与实现细节见 `docs/dynamic-data.md §13.3`。
