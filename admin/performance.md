# 性能与压测

静态招牌几乎不耗性能，你不需要为挂几十面招牌担心。这一页讲清楚它为什么这么省，怎么用内置压测工具实测你这台服务器的余量，以及那些"上限"配置到底是什么意思。

## 静态招牌几乎不耗性能

一面**不动的招牌**在做好之后就**不再刷新**——它停在那里，服务器一帧都不会为它重画。只有两种情况会触发重画：

- 有人正在编辑这面招牌。
- 招牌上绑的数据变了（比如显示列车时刻、计分板的招牌）。

所以你大可放心：满世界挂静态招牌，平时的开销基本是零。真正吃性能的是会动的招牌（时间轴动画、补间动画、脚本驱动），而那些也由你自己决定开不开。

## 用 /canvas bench 实测开销

想知道你这台服务器一面招牌渲染要花多少时间？用内置压测命令实测，不用猜：

```
/canvas bench run
```

它会在**后台**用一批程序生成的测试画面，模拟真实的渲染过程，测出每种画面的渲染耗时和调色板匹配耗时，然后把结果发到你聊天栏，并存一份报告。

::: tip 只测渲染本身
压测**只测渲染计算（画图 + 配色），不测网络、不测带宽、不模拟玩家连接**。它告诉你的是"这台机器画一面招牌要多久"，剩下的（多少人在线、网络好不好）由你的实际情况决定。
:::

常用子命令：

| 命令 | 作用 |
|---|---|
| `/canvas bench list` | 看有哪些测试画面 |
| `/canvas bench run` | 跑一次完整压测，出报告 |
| `/canvas bench run <画面>` | 只测某一类画面 |
| `/canvas bench report` | 重新打印最近一次的报告 |
| `/canvas bench clear` | 清掉已保存的报告 |

报告文件存在插件数据目录的 `benchmarks/` 下，里面有一份网页版报告，浏览器打开就能看图。

## 报告能帮你估算挂多少招牌

报告不只给原始耗时，还会按**目标帧时间**帮你换算：在你设定的每帧预算内，这台服务器大概还能扛多少面招牌一起重画。

这对规划很有用。比如你想做一片会动的招牌墙，先跑一次压测，报告会告诉你"以你这台机器的速度，同时动这么多面会不会超时"。把决策权交给数据，而不是上线后才发现卡。

针对会动的内容，还有两个专门的压测：

```
/canvas bench run-tween     # 补间动画的帧开销
/canvas bench run-script    # 脚本动作链的开销
```

## 设计原则：插件不替你做主

HikariCanvas 有一条贯穿始终的原则——**工具不是保姆**：

- **不偷偷降画质**。无论挂多少招牌、画面多复杂，插件都不会背着你压缩质量、降低分辨率来"保平安"。
- **配置里的上限只是安全阀**。它们存在的意义是防极端情况（比如某个脚本失控刷爆），不是用来自动调优的。正常情况下你碰不到这些上限。
- **数据摆给你，你来决定**。挂多少面、开多高帧率、动画做多复杂，全由你定。插件负责把真实开销告诉你（这就是压测的用处），但不自作主张。

简单说：它假设你知道自己在做什么，把控制权留给你。

## 和性能相关的上限在哪调

下面这些上限默认值就够用，只有你确实要做大量动态内容、或想给整台服务器加保险时才需要动。全部在[配置](/admin/config)里：

| 上限 | 管什么 |
|---|---|
| 投影帧率 | 编辑 / 数据变化时，招牌最多每秒重画几次 |
| 时间轴最大帧率 | 单面墙时间轴动画的帧率硬上限 |
| 补间最大帧率 | 补间动画的帧率硬上限 |
| 脚本预算 | 单次脚本触发最多执行多少动作、每秒最多触发几次 |

这些是"管理员给整台服务器加的总阀门"，插件不会自动去碰它们。详细说明和默认值见[配置](/admin/config)。
